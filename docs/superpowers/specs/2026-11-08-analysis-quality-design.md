# 분석 품질 개선: 충돌 추정, 근거 시각, 법적 근거

2026-11-08. 현재 상태와 실험 기록은 `docs/analysis-quality.md`에 있다.

## 목적

분석이 사고 영상의 대부분을 "사고 장면 미확인"으로 끝낸다. 정답이 사고인 영상 18개 중 12개다. 블랙박스에는 접촉 순간이 잘 찍히지 않는데, 지금은 AI가 프레임에서 접촉을 보지 못하면 바로 판단을 끝내기 때문이다.

사람은 화면에 접촉이 안 보여도 다른 단서로 충돌을 알아챈다. 사용자가 꼽은 단서는 세 가지다.
- 충돌음
- 화면 흔들림
- 상대 차 급정지

이 단서를 판단에 넣는다. 여기에 두 가지를 함께 개선한다.
- 레포트의 타임라인 시각이 영상과 맞는지 보장한다.
- 과실 판단의 법적 근거(관련 법규, 판례)를 레포트에 보인다.

## 목표

1. 상대 차 급정지를 충돌 후보 신호에 추가한다.
2. 프레임에서 접촉이 안 보여도, 센서 신호가 함께 강하게 잡히면 "충돌 추정"으로 판단을 이어 간다.
3. 레포트의 모든 근거 시각이 실제 영상 장면과 맞게 한다.
4. 도표마다 관련 법규와 판례를 수집해 레포트 "기준"에 보인다.

## 하지 않는 것

- Jev 같은 외부 판단 모델. 입력이 숫자 몇 개이고 평가할 사고 영상이 18개뿐이라, 규칙과 차이를 확인하기 어렵다. 정답이 확인된 영상이 100개 이상 쌓이고 규칙이 더 오르지 않을 때 다시 검토한다. `docs/analysis-quality.md`에 적는다.
- 정답 라벨의 팀 확인. 초안 정답으로 진행하고, 모든 결과에 "초안 정답 기준"이라고 적는다.
- "충돌 추정"용 새 레포트 항목. 기존 요약 문장과 신뢰도로 표시한다.
- 에뮬레이터를 쓰는 테스트. 평가 도구, pytest, 웹과 앱의 단위 테스트로만 확인한다.

## 실패로 보는 것

- 사고 없는 영상에 과실을 표시하는 것. 지금 0/7이고, 이 값을 유지해야 한다.
- 레포트의 근거 시각을 눌렀는데 그 장면에 해당 내용이 없는 것
- 추정인데 확인된 것처럼 보이는 것
- 협회 해설 글처럼 저작권이 있는 글을 옮기는 것

## 설계

### 1. 상대 차 급정지 신호 (`pipeline/locate.py`)

- 추적 중인 차의 속도가 짧은 구간 안에 크게 줄어드는 순간을 점수로 만든다. 속도는 상자 중심과 크기 변화로 어림한다.
- 대상은 내 진행 경로에 있거나 경로에 가까운 차다. 기존 `_risk`, `LANE_HALF` 기준을 따른다.
- 기존 세 신호(상자 급변 `box`, 흔들림 `motion`, 소리 `audio`)에 네 번째 신호(`decel`)로 더한다. 가중치와 임계값은 평가로 정한다.
- 후보(`Candidate.signals`)에 각 신호의 값과, 그 신호가 가장 크게 잡힌 시각을 함께 남긴다. 시각은 아래 2번과 3번에서 쓴다.

### 2. 충돌 추정 (`pipeline/assess.py`, 필요하면 `observe.py`)

- **발동 조건:** 관찰 단계가 `collision_t`를 내지 못했고(`none`이거나 `collision_t`가 null), 어떤 후보에서 다음 두 조건이 모두 성립할 때만 추정한다.
  - 세 단서(충돌음, 흔들림, 상대 차 급정지) 중 두 개 이상이 강하게 잡힌다.
  - 그 신호들의 시각이 서로 가깝다(기존 `ALIGN_S` 범위).
- **대상:** 추정은 촬영 차가 당사자인 경우(`party`)만 한다. 흔들림이 자기 차 충격의 근거이므로 흔들림은 필수다. 다른 차끼리 부딪힌 경우(`witness`)는 추정하지 않는다.
- **추정할 때:**
  - `collision_t`는 그 후보 시각이다.
  - 각 신호의 시각에 사실 항목을 추가한다. 예: "충돌음이 크게 남", "화면이 크게 흔들림", "앞차가 급정지함". 이 항목들은 기존 `Evidence(t, text)` 형식이고, 시각이 신호가 잡힌 실제 시각이라 영상과 맞는다.
  - 이후 도표 선택과 과실 계산은 지금처럼 진행한다. 장면 유형은 관찰 단계의 `scene`을 쓴다.
  - 표시: 요약 문장 앞에 "충돌 추정:"을 붙인다. 신뢰도는 "낮음"으로 고정한다. 신뢰도 설명 문구는 기존 것을 쓴다.
- **추정하지 않을 때:** 지금처럼 "사고 장면 미확인"과 이유를 보인다.

### 3. 근거 시각 검증 (`pipeline/assess.py`, `report.py`)

- 레포트의 모든 시각(`timeline`, `facts`, 수정요소 근거, 12대 중과실 근거, 유리·불리 주장)은 다음 중 하나여야 한다.
  - 실제로 AI에 보여 준 프레임의 시각 근처(`NEAR_FRAME_S` 이내)
  - 2번에서 넣은 센서 신호의 시각
- 둘 다 아니면 지금처럼 그 항목을 버린다. 이미 있는 검사가 모든 항목에 빠짐없이 적용되는지 확인하고, 빠진 곳은 막는다.
- **평가 지표:** `evaluate`의 "근거 시각 표본 검사"를 실제로 측정한다. 영상마다 근거 항목을 뽑아 30개 이상 모은다. 각 시각의 프레임을 사람이 보고 맞는지 판정할 수 있게 표를 만든다. 판정은 controller나 사용자가 프레임 이미지를 보고 한다.

### 4. 법적 근거 (`data/fault_charts.json`, 수집 스크립트, 레포트, 웹, 앱)

- **수집:** `apps/api/scripts/`에 과실비율정보포털 도표 페이지(`source`)에서 다음을 모으는 스크립트를 둔다. 24개 도표에 한 번 돌려 결과를 `fault_charts.json`에 넣고 커밋한다.
  - "관련 법규": 법령 이름, 조 번호, 조 제목
  - "판례·조정사례": 법원, 선고일, 사건번호
- **옮기는 범위:**
  - 조문 본문과 판결 요지는 저작권 보호 대상이 아니지만, 길어서 레포트에 넣지 않는다. 링크로 원문을 연다.
  - 법령은 국가법령정보센터 조문 링크를 쓴다. 판례는 사건번호와 출처 페이지 링크를 쓴다.
  - 협회의 "기본 과실 해설"은 옮기지 않는다.
- **레포트:** `FaultAssessment`에 선택 항목 `laws`와 `cases`를 추가한다. 기존 클라이언트는 이 항목을 무시하므로 깨지지 않는다.
  - `laws`: `{name, article, title, url}` 목록
  - `cases`: `{court, date, number, url}` 목록
- **표시:**
  - 웹 레포트와 앱 레포트 "기준" 탭에 "관련 법규"와 "참고 판례" 목록을 둔다. 누르면 원문 링크를 연다.
  - 앱 PDF(`report-html.ts`)에도 넣는다.
  - 앱 표시는 다음 APK부터 보인다.
- 수집이 실패한 도표는 빈 목록이다. 화면은 목록이 비면 그 영역을 숨긴다.

## 측정과 합격선

- 합격선은 `docs/analysis-quality.md`와 같다.

  | 지표 | 합격선 |
  |---|---|
  | 충돌 시각 1초 이내 | 80% |
  | 정답 도표 | 70% |
  | 정답 과실이 범위 안 | 70% |
  | 사고 없는 영상에 과실 표시 | 0건 |
  | 근거 시각 일치 | 표본 30개 이상, 90% |

- **임계값 조정:** `tuned` 분할로 정하고, `t8_only`와 `held_out`으로 확인한다.
- **비용:**
  - 비용이 들지 않는 재채점(`--rescore`)과 기존 결과의 원인 분석을 먼저 한다. 놓친 12개가 후보 단계에서 빠졌는지, 판단 단계에서 빠졌는지 나눈다.
  - 전체 재측정(OpenAI 약 10달러)은 사용자 승인 뒤에 한다.
- **결과 기록:** README 평가 결과와 `docs/analysis-quality.md`를 갱신한다. 합격선에 못 미치면 못 미친 그대로 적는다.

## 배포

- 레포트 형식에는 선택 항목만 추가한다. DB 변경은 없을 것으로 본다(레포트는 JSON 컬럼).
- API 응답 타입이 바뀌므로 `openapi.json`과 웹·앱 생성 타입을 다시 만든다.
- **배포 순서:**
  1. API와 worker를 올린다. 처리 중인 분석이 없을 때 한다.
  2. 웹을 다시 배포한다.
  3. 운영 웹에서 분석 한 건을 끝까지 확인한다.
- 앱은 다음 APK 릴리즈에 포함한다. 배포와 릴리즈는 사용자 지시를 받아서 한다.

## 세부 결정 (검토 질문에 대한 답)

1. **관찰이 `none`일 때의 당사자 판정:** 센서 조건을 당사자 판정의 대리로 쓴다. 흔들림이 필수이고, 흔들림은 촬영 차에 충격이 왔다는 근거이기 때문이다. 관찰 프롬프트는 바꾸지 않는다.
   - 장면 유형은 관찰 결과의 `scene`을 쓴다. `involvement`가 `none`이어도 `scene`은 항상 나오는 필드다.
   - `scene`이 `other`이거나 도표 후보가 없으면 과실은 내지 않는다(`fault` null, `fault_note`에 이유). 충돌 추정과 타임라인은 그대로 보인다.
2. **원인 분석:** 평가 영상 36개는 모두 있다. `eval/videos`에 6개, `~/workspace/university/사고영상`에 30개다.
   - 후보 단계(YOLO, 추적, `locate`)는 로컬에서 돌아 비용이 없다. 영상마다 후보 시각과 신호값을 다시 계산해, 정답 충돌 시각이 후보에 들었는지 표로 만든다.
   - `evaluate`가 결과에 후보와 신호값(trace)을 저장하도록 고친다. 이후 측정부터는 원인 분석을 다시 돌리지 않아도 된다.
   - LLM을 부르는 전체 재측정만 승인 뒤에 한다.
3. **합격선과 우선순위:** 사고 없는 영상의 과실 표시 0건이 최우선이다. 임계값은 이 조건을 지키는 범위에서 사고 검출을 최대로 하도록 정한다. 다른 합격선에 못 미쳐도 구현과 측정은 끝까지 하고, 결과를 그대로 적는다.
   - 충돌 시각 지표는 센서 추정에서 불리할 수 있다. 흔들림과 소리는 접촉 뒤에 온다. 그래서 추정의 `collision_t`는 신호들 중 가장 이른 시각(보통 상자 급변이나 급정지 시작)으로 한다.
4. **센서 사실의 처리:**
   - 센서 사실은 판단 모델(assess LLM)에 넣지 않는다. 모델이 끝난 뒤 코드가 `timeline`에 시간순으로 붙인다. 그래서 심각도나 12대 중과실 판단에 쓰이지 않는다.
   - 추정 경로는 "충돌 시각 곁에 프레임 사실이 있어야 함" 검사를 거치지 않는다. 대신 위의 발동 조건이 그 역할을 한다.
   - `Evidence`에 형식 변경은 하지 않는다. 출처 구분은 코드 내부(사실 목록을 따로 들고 다님)에서만 한다.
   - 근거 시각 표본 검사는 센서 사실과 프레임 사실을 따로 세서 보고한다. 합격선(90%)은 프레임 사실 기준이다.
5. **법적 근거 수집:**
   - 포털 페이지는 서버에서 HTML로 내려와 "관련 법규"와 "판례·조정사례" 글이 들어 있다(2026-11-08 확인). 단순 HTTP 요청으로 파싱한다. 24개 페이지를 한 번만, 요청 사이에 간격을 두고 받는다.
   - 가져오는 것은 법령 이름, 조 번호, 조 제목, 법원, 선고일, 사건번호 같은 사실 정보뿐이다.
   - 법령 링크: `https://www.law.go.kr/법령/{법령명}/제{N}조`
   - 판례 링크: `https://www.law.go.kr/판례/({사건번호})`. 대법원 외 판례처럼 링크가 열리지 않을 수 있는 것은 사건번호만 보이고 링크는 출처 페이지로 한다.
   - 포털이 막히거나 구조가 달라 수집이 안 되면 목표 4는 보류하고 나머지를 진행한다. 다른 출처는 쓰지 않는다.

## 내 판단으로 정한 것

- 추정은 `party`만 하고 흔들림을 필수로 한 것. 사고 없는 영상의 오탐을 막기 위해서다.
- 추정이면 신뢰도를 "낮음"으로 고정하고 요약 앞에 "충돌 추정:"을 붙이는 방식
- 법규와 판례는 번호, 제목, 링크만 담고 본문은 넣지 않는 것
- `laws`와 `cases`의 필드 이름

## 구현하는 사람이 정할 것

- 급정지 점수 계산 방식과 임계값의 구체 값(평가로 정한다)
- 포털 페이지 파싱 방식
- 웹과 앱의 목록 표시 세부 모양(기존 디자인 시스템 안에서)
